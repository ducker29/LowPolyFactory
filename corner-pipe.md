# Инструкция агенту: угловая труба и угловой слот

## Цель

Реализовать в существующей системе `FactoryPipePower` новый тип трубы — **угловую направленную трубу** — и соответствующий **угловой слот**.

Агент должен самостоятельно:

- провести короткий аудит актуального кода и структуры существующих прямых труб;
- добавить необходимые данные и проверки;
- создать рабочий prefab угловой drag-трубы;
- создать рабочий prefab углового слота;
- настроить mesh, материалы, коллайдеры и ссылки компонентов;
- встроить угловую трубу в существующую логику установки, вращения, визуальных состояний и передачи питания;
- проверить компиляцию и целостность созданных prefab-ов.

Не ограничиваться отчётом или планом: в рамках описанного scope нужно создать функционал и проектные ассеты.

Ручную проверку выполняет пользователь. Автоматические тесты и PlayMode не запускать.

---

## Подтверждённые требования

### Форма трубы

Добавить отдельный тип формы трубы:

```text
Straight
Corner
```

Требования к сериализации:

- `Straight` должен иметь числовое значение `0`;
- `Corner` должен иметь следующее свободное значение;
- существующие прямые трубы и слоты после добавления поля должны остаться `Straight`;
- нельзя определять форму по имени mesh, prefab или GameObject;
- форма должна храниться в штатных gameplay-данных трубы и слота.

Совместимость при установке:

- `Straight`-труба принимается только `Straight`-слотом;
- `Corner`-труба принимается только `Corner`-слотом;
- существующие проверки диаметра, размера и других параметров сохранить;
- совпадение диаметра не должно позволять установить прямую трубу в угловой слот или угловую трубу в прямой слот.

---

## Обязательный mesh

Для обоих новых prefab-ов использовать существующий mesh:

```text
SM_Factory_Small_pipe_Corner
```

Один и тот же mesh использовать:

- в `Visual` угловой drag-трубы;
- в `SlotPipeVisual` углового слота.

Перед созданием prefab-ов найти фактический asset path и соответствующий mesh subasset.

Запрещено:

- подменять модель прямой трубой;
- использовать Unity-примитив вместо указанного mesh;
- использовать другой угловой mesh;
- изменять исходный mesh;
- применять изменения к import settings модели без доказанной необходимости;
- переносить или перепекать авторский pivot исходного ассета.

Суффикс `(1)` у экземпляра на скриншоте не является частью имени mesh.

Поворот `Y = -90°`, который мог быть виден у экземпляра модели, не считать доказательством исходной ориентации mesh. Фактическую базовую ориентацию определить по геометрии asset-а.

## Система направлений

Углы обозначают направление отверстия **наружу из трубы** в мировом пространстве:

```text
0°   = +Z
90°  = +X
180° = -Z
270° = -X
```

Соединяемые отверстия должны смотреть навстречу друг другу.

Использовать правило:

```text
Opposite(angle) = (angle + 180) mod 360
```

Не сравнивать наружные направления соединяемых концов на простое равенство.

Все углы нормализовать к одному из четырёх значений:

```text
0, 90, 180, 270
```

Для определения четверти использовать существующий `QuarterTurnUtility` или его текущий эквивалент. Не использовать прямое сравнение float-углов.

---

## Прямая труба

Существующие прямые трубы остаются двусторонними.

Сохранить существующие группы с `OR`:

```text
Yaw0Or180
Yaw90Or270
```

Фактические открытые направления прямой трубы определяются её текущим игровым поворотом:

| Фактическая ось | Открытые направления |
|---|---|
| 0° / 180° | 0° и 180° |
| 90° / 270° | 90° и 270° |

При сравнении с прямой трубой разрешается совпадение с любым подходящим концом из её фактической пары `OR`.

Не выдавать настроенную целевую `rotationGroup` за фактический текущий поворот трубы.

Если одновременно проверяются предыдущий и следующий соседи одной прямой трубы, один физический конец нельзя использовать для обеих сторон. Проверка считается правильной, только если существует распределение, при котором предыдущий и следующий соседи используют разные противоположные концы прямой трубы.

Существующее поведение прямых труб не должно регрессировать.

---

## Угловая труба

У угловой трубы концы имеют фиксированные роли:

```text
Input
Output
```

Это направленная труба:

- `Input` и `Output` не являются `OR`;
- `Input` и `Output` не меняются ролями после вращения;
- обратное направление потока автоматически не допускается.

Базовое игровое положение:

```text
Input = 0°
Output = 90°
```

Добавить отдельную типизированную группу угловой ориентации, например `CornerRotationGroup`, либо эквивалентную структуру данных.

Не пытаться представить угловые пары существующим enum прямых `OR`-групп.

Обязательные четыре положения:

| Поворот модели | Input | Output |
|---:|---:|---:|
| 0° | 0° | 90° |
| 90° | 90° | 180° |
| 180° | 180° | 270° |
| 270° | 270° | 0° |

Если используется enum, рекомендуемые смысловые значения:

```text
Input0Output90
Input90Output180
Input180Output270
Input270Output0
```

Не менять числовые значения существующих enum.

---

## Настройка углового слота

Угловой слот должен иметь настраиваемую требуемую угловую группу из четырёх вариантов.

Для `Corner`:

- текущие `Input` и `Output` вычисляются из фактического поворота установленной трубы;
- `IsAligned` истинен только тогда, когда текущая упорядоченная пара `Input → Output` совпадает с настроенной группой углового слота;
- пара `0 → 90` не равна паре `90 → 0`;
- существующий `rotationGroup` прямых труб не использовать как источник истины для Corner.

Для `Straight` оставить существующую OR-проверку.

---

## Проверка соседних труб

Соседство определяется существующими ссылками цепочки `previous / next`.

Запрещено:

- искать ближайшие трубы;
- использовать overlap-запросы для определения соседа;
- проверять расстояние между слотами или портами;
- требовать физического контакта коллайдеров;
- автоматически переставлять слоты.

Пользователь вручную размещает слоты на правильном расстоянии. Код проверяет только форму, текущую ориентацию и направления концов.

### Универсальная проверка пары

Для пары `Previous → Current`:

#### Previous = Straight, Current = Straight

Проверить, что существует пара фактических открытых направлений, которые смотрят навстречу:

```text
Opposite(previousEnd) == currentEnd
```

#### Previous = Straight, Current = Corner

Для входа текущего уголка использовать строго `Current.Input`.

Проверка:

```text
Opposite(Current.Input)
```

должен совпасть с любым фактическим открытым направлением предыдущей прямой трубы.

#### Previous = Corner, Current = Straight

У предыдущего уголка использовать строго `Previous.Output`.

Проверка:

```text
Opposite(Previous.Output)
```

должен совпасть с любым фактическим открытым направлением текущей прямой трубы.

#### Previous = Corner, Current = Corner

Использовать только направленные концы:

```text
Opposite(Previous.Output) == Current.Input
```

### Проверка выхода текущего уголка

Для пары `Current → Next`:

- если `Next` является `Straight`, `Opposite(Current.Output)` должен совпасть с любым фактическим открытым направлением следующей прямой трубы;
- если `Next` является `Corner`, должно выполняться `Opposite(Current.Output) == Next.Input`.

### Использование концов Straight

Если у прямой трубы присутствуют оба соседа, определить множества допустимых концов для предыдущего и следующего соединения.

Соединение всей прямой трубы допустимо только тогда, когда можно выбрать два разных конца:

```text
previousEndIndex != nextEndIndex
```

Не разрешать логически подключить предыдущего и следующего соседа к одному физическому концу прямой трубы.

## Локальная ориентация и питание

Не смешивать два понятия:

1. `IsAligned` — труба соответствует требуемой ориентации своего слота.
2. `IsConnectedToPrevious / IsConnectedToNext` или эквивалентная внутренняя проверка — фактические направления соседних установленных труб совместимы.

Ожидаемая логика состояний сохраняется:

| Ситуация | Результат |
|---|---|
| Неправильная ориентация относительно слота | `OccupiedWrongRotation`, материал `M_Pipe_Default` |
| Правильная ориентация, но питание ещё не пришло | `OccupiedAligned`, оранжевый `M_Slot_Wrong` |
| Правильное входное соединение и предыдущий узел запитан | `Charging`, затем `Powered`, зелёный runtime fill |

Не возвращать старое соответствие материалов.

Согласованная текущая схема:

```text
OccupiedWrongRotation → defaultMaterial / M_Pipe_Default
OccupiedAligned       → wrongMaterial / M_Slot_Wrong (оранжевый)
Charging / Powered    → green runtime material
```

Питание не должно проходить через несовместимое соединение.

Для перехода питания от предыдущей трубы к текущей требуется:

- текущая труба установлена;
- текущая труба локально правильно ориентирована;
- предыдущий узел запитан;
- соединение `Previous → Current` совместимо по правилам выше.

Следующая труба при своей проверке использует выход текущей трубы.

Пустой следующий слот не должен мешать текущей трубе отображаться как локально правильно ориентированная. Отсутствие следующей трубы означает отсутствие выходного соединения, но не превращает правильную ориентацию текущего слота в неправильную.

После установки или разрешённого поворота трубы пересчитать:

- её текущие направления;
- её локальное `IsAligned`;
- соединение с предыдущим соседом;
- соединение со следующим соседом;
- затронутые состояния соседних слотов и возможность дальнейшей передачи питания.

Не перестраивать всю цепь каждый кадр. Выполнять пересчёт по событиям установки, поворота, reset и изменения питания.

Не разрешать вращение уже заблокированных состояниями `Charging / Powered`, если текущая FSM это запрещает.

## Start и End

Сначала прочитать текущую реализацию `StartPowerNode`, `EndPowerNode` и `PowerChainController`.

Не добавлять проверку расстояний.

Если Start/End не имеют направленных портов, не выполнять широкий редизайн без необходимости. Для граничных элементов использовать минимальное решение, совместимое с существующей цепочкой:

- первый слот получает питание от Start по существующему механизму;
- последний слот передаёт питание End по существующему механизму;
- угловая логика между слотами обязана работать полностью;
- локальная требуемая группа первого/последнего углового слота остаётся источником правильной ориентации на границе.

Если для корректного ограничения первого или последнего соединения действительно требуется направление Start/End, добавить его как явную сериализованную настройку, не вычисляя по имени или позиции. В отчёте объяснить необходимость.

Не ломать уже исправленный зелёный визуал StartPowerNode.

## Pivot установки и центр вращения

Это обязательное требование.

### Установка

Угловая drag-труба должна привязываться к слоту по **текущему авторскому pivot mesh**.

Запрещено менять pivot исходной модели.

Точка snap углового слота должна соответствовать авторскому pivot mesh в базовой игровой ориентации.

### Вращение

После установки угловая труба должна вращаться вокруг **геометрического центра модели**, а не вокруг авторского pivot.

Центр определить по фактической геометрии и bounds указанного mesh. Не брать координаты на глаз со скриншота.

Рекомендуемая иерархия углового слота:

```text
PF_PipeSlot_Small_Corner
├── AnchorY                 # расположен в центре вращения модели
│   ├── SlotPipeVisual      # компенсирующее смещение сохраняет исходный pivot/snap
│   └── TapCollider         # вращается вместе с видимой трубой
├── ConnectorA / Input marker, если нужен текущей архитектуре
├── ConnectorB / Output marker, если нужен текущей архитектуре
└── CaptureVolume
```

Точное имя `AnchorY` сохранить, если его ожидает существующий код.

Требования:

- root углового слота остаётся точкой установки по авторскому pivot;
- `AnchorY` размещается в геометрическом центре модели;
- `SlotPipeVisual` получает компенсирующее локальное смещение, чтобы при yaw `0°` mesh находился точно там же, как при размещении по исходному pivot;
- при вращении меняется yaw `AnchorY`;
- `SlotPipeVisual` и `TapCollider` вращаются вместе вокруг центра;
- после четырёх поворотов по 90° объект возвращается в исходное положение без накопления ошибки;
- нельзя менять исходный pivot mesh или запекать новый pivot в asset.

Если базовая локальная ориентация mesh не соответствует `Input=0° / Output=90°`, создать корректный transform alignment внутри prefab-а. Не изменять import rotation исходного asset-а только ради gameplay-ориентации.

## Prefab угловой drag-трубы

Создать проектный prefab с именем, согласованным с текущим naming convention. Предпочтительное имя:

```text
PF_DraggablePipe_Small_Corner.prefab
```

Prefab должен быть создан по структуре существующей рабочей Small drag-трубы, но с угловой формой и обязательным mesh `SM_Factory_Small_pipe_Corner`.

Настроить:

- gameplay spec / данные формы `Corner`;
- диаметр Small;
- визуал;
- материалы по существующим ссылкам;
- Rigidbody и drag-поведение согласно рабочему прямому prefab-у;
- drag collider по фактической геометрии углового mesh;
- layer и mask согласно существующей системе;
- tutorial overlay, если он является обязательной частью текущего drag-prefab-а;
- исходный pivot root для snap.

Не включать обратно drag collider после commit. Существующая исходная drag-труба после установки должна скрываться так же, как прямые трубы.

Коллайдер не должен быть заведомо расположен как у прямой трубы. Измерить corner mesh.

Допустимо использовать минимальный compound collider, если один BoxCollider создаёт чрезмерно большую пустую область. Не менять общий Input-код без необходимости.

## Prefab углового слота

Создать проектный prefab с именем, согласованным с текущим naming convention. Предпочтительное имя:

```text
PF_PipeSlot_Small_Corner.prefab
```

Создать его на основе структуры актуального рабочего Small-слота, но не копировать геометрию прямой трубы вслепую.

Настроить:

- форму `Corner`;
- требуемую `CornerRotationGroup`;
- обязательный mesh `SM_Factory_Small_pipe_Corner`;
- `SlotPipeVisual`;
- `AnchorY` в геометрическом центре модели;
- компенсирующий offset визуала;
- `CaptureVolume` в области исходного pivot установки;
- tap collider, следующий за видимой трубой;
- существующие материалы Empty, HoverValid, Default, Orange и GreenFill;
- ссылки `previous / next` оставить настраиваемыми в сцене;
- layer `PipeSlot` для tap collider;
- `isTrigger=false` для collider, используемого tap-raycast, если текущий Input использует `QueryTriggerInteraction.Ignore`.

Существующий путь:

```text
hit.collider.GetComponentInParent<PipeSlotController>()
```

или его актуальный эквивалент должен продолжать определять слот по дочернему collider без специального поиска по имени.

Не возвращать неподвижный root tap collider, если актуальная рабочая система уже использует collider под `AnchorY`.

Пользователь подтвердил, что текущая реализация tap collider работает правильно. Не выполнять дополнительные несогласованные изменения его жизненного цикла.

---

## Коллайдер установленной угловой трубы

Tap collider должен:

- совпадать с видимой угловой трубой достаточно точно для ручного тапа;
- вращаться вместе с `AnchorY`;
- не оставлять неподвижную область на старом положении;
- позволять тап по обоим плечам уголка;
- использовать существующий `TryRotateTap`;
- не требовать изменений `PointerInputController`, если текущий `GetComponentInParent` уже работает;
- не конфликтовать с `CaptureVolume`.

Для L-образной геометрии предпочтителен минимальный compound collider из двух BoxCollider либо корректный MeshCollider, если он совместим с текущей физикой и Input. Не использовать огромный bounding box, если он создаёт явно кликабельную пустую внутреннюю область уголка.

Если текущий `PipeSlotController` хранит только одну ссылку `tapCollider`, выбрать минимальное решение:

- родительский объект `TapCollider` под `AnchorY`;
- дочерние collider-компоненты либо расширение управления набором colliders;
- включение/выключение всей tap-области единым способом;
- без дублирования старого неподвижного collider.

Не менять уже подтверждённое пользователем поведение существующих прямых slot-collider-ов.

## Вращение

Установленная угловая труба вращается по тапу шагом `+90°` вокруг `AnchorY`.

Последовательность должна соответствовать:

```text
0°   : Input 0°   → Output 90°
90°  : Input 90°  → Output 180°
180° : Input 180° → Output 270°
270° : Input 270° → Output 0°
```

После `270°` следующий поворот возвращает `0°`.

Не менять направление шага существующего пользовательского ввода, если прямые трубы уже вращаются согласованно.

Не вычислять пару Corner независимыми ручными таблицами в нескольких классах. Создать один источник истины — utility, типизированные данные или методы spec/slot.

## Визуальные состояния и зелёный fill

Угловая труба должна использовать существующую систему материалов:

- пустой слот;
- hover valid;
- неправильная ориентация — default;
- правильная ориентация без питания — orange;
- charging / powered — green runtime material.

Обязательный результат:

- Corner в `Powered` полностью зелёный;
- отсутствие настроенного flow не должно давать серый визуал;
- существующий fallback flow в `PipeVisualController` не ломать;
- существующие прямые трубы должны продолжать заполняться как раньше.

Сначала проверить, способен ли текущий `GreenFill` корректно отобразить угловой mesh.

Не выполнять широкий редизайн общего shader-а, если для функциональности достаточно корректно настроенного runtime flow и полного зелёного состояния.

Если линейный shader не может визуально пройти по L-образному пути, допустимо для Corner сохранить существующую длительность `Charging`, а затем показывать полностью зелёный `Powered`. Не ломать shader прямых труб ради сложной анимации уголка.

Любое изменение общего shader-а требует доказательства необходимости и отдельного перечисления рисков в отчёте.

## Ожидаемая ручная проверка

13. Previous Corner сравнивается строго по Output.
14. Next Straight сравнивается по любому концу OR.
15. Next Corner сравнивается строго по Input.
16. Powered Corner полностью зелёный.
17. Существующие прямые трубы работают как раньше.
